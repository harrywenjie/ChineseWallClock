# 2026-07-23 K4-03 Deployment Record

This page reconstructs the actual fork deployment from a user-provided Codex chat log. It is the operational record for the recorded successful flash of the replacement firmware on the **BAIYANGSHU WiFi Clock K4-03** (not the upstream K2-02).

## 1. Source and privacy

- **Source:** a Codex session log supplied by the maintainer on 2026-11-08. The chat excerpt shows a shell timestamp of 14:52 but no date; the build artifacts date the session to **2026-07-23**. Treat the date as inferred, not separately verified.
- **Redactions:** this public record omits the MAC address, Wi-Fi SSID, LAN addresses, AP chip suffix and the private backup path. Those values remain in the maintainer's private notes. Do not add them back to the repository.
- **Backup warning:** the full K4-03 factory backup contains the ESP8266 SDK Wi-Fi credentials. It must not be copied into Git, attached to an issue, or shared publicly.

## 2. Target hardware

| Item | Value |
|---|---|
| Clock board | BAIYANGSHU WiFi Clock **K4-03** (actual unit) |
| Upstream reference | BAIYANGSHU 1902 WiFi Clock **K2-02** (do not assume electrical equivalence) |
| MCU | ESP8266EX, 26 MHz crystal |
| Flash | 4 MB |
| USB-UART | Silicon Labs CP210x on `COM3` |
| Clock power | Its own USB-A supply; CP2102 `+5V`/`3V3` not connected |
| UART wiring | CP2102 `GND` → board `GND`; CP2102 `TXD` → board `RXD0`; CP2102 `RXD` → board `TXD0` |
| Flash mode | Manual: `FLASH`/GPIO0 → `GND`, then repower the clock |
| Reset lines | CP2102 `RST`/`DTR`/`RTS` not connected; **no automatic reset** |

Confirmed six-pin header at the time of deployment: pin 1 `FLASH`/GPIO0, pin 2 likely `RST`, pin 3 `GND`, pins 4/5 `RXD0`/`TXD0`, pin 6 `+5V`. UART communication was tested before flashing.

Because there is no automatic reset, every esptool command used:

```text
--before no-reset --after no-reset
```

## 4. Build

- Build system: Arduino sketch via Arduino CLI.
- Final tool: Arduino CLI **0.35.3** (the version bundled with Arduino IDE 2.3.2).
- Core: ESP8266 **3.1.2**.
- Libraries: the repository's `libraries/libraries.zip` snapshot; no latest-version replacements.
- FQBN: `esp8266:esp8266:d1_mini`.
- Board parameters: 80 MHz CPU, 4 MB flash, `4M2M` layout (2 MB LittleFS, ~1019 KB OTA sketch), DIO, 40 MHz, lwIP v2 Lower Memory, 32 KB cache + 32 KB IRAM, exceptions/debug/stack protection off, `-Os`, NONOS SDK 2.2.x_190703, xtensa-lx106 GCC 10.3.
- Reproducibility: the ESP8266 core embeds a build timestamp. The final build fixed `SOURCE_DATE_EPOCH=1711661163` (the last firmware source commit time, 2024-03-28T22:26:03+01:00). Two independent clean builds then produced byte-identical `.bin` files.
- Final image: `temp/artifacts/canonical1/ChineseWallClock.ino.bin`, **485,280 bytes**, SHA-256 `5E4F281421DCE894FED3F03DD9599AF8A690218A85C70B6A5A5DB466748D3D1D`.
- Other outputs: ELF 7,910,136 bytes; map 4,689,021 bytes; verbose log `temp/logs/build-canonical-ide232-cli.log`.
- Resource use: RAM 37,404 / 80,192 (46 %), IRAM 62,551 / 65,536 (95 %), flash code 443,980 / 1,048,576 (42 %).
- The upstream v1.1 image is 485,248 bytes; the 32-byte difference was not resolved. The image header is the same class (ESP8266, 4 MB, DIO, 40 MHz).

The image is a single combined image: eboot at `0x000000`, application at `0x001000`; app ELF entry `0x401000C0`, IROM `0x40201010` (443,980 bytes). No separate filesystem image is generated; the web UI is compiled into WiFiManager.

## 5. Pre-flash checks

Before writing, the backup and firmware hashes were re-checked, the bootloader connection was confirmed, and the serial monitor was closed. The flash command was prepared with:

- no full-chip erase;
- no separate filesystem upload;
- `--before no-reset --after no-reset`;
- conservative `115200` baud;
- `--flash-mode keep --flash-freq keep --flash-size keep` so the existing flash parameters were preserved.

```powershell

  --flash-mode keep --flash-freq keep --flash-size keep `
  0x000000 `
  E:\ChineseWallClock\temp\artifacts\canonical1\ChineseWallClock.ino.bin
```

Result:

- Erased only the sectors needed for the image: `0x000000–0x076FFF`.
- Wrote **485,280 bytes**.
- esptool automatic verification: `Hash of data verified`.
- Independent verification:


- No full-chip erase was performed.
- The device remained in the bootloader after verification.

- The time initially displayed Europe/Budapest because that is the default timezone. This is a configuration issue, not an NTP failure.

Note that `clever` is absent: this is the known `saveConfiguration()` defect, not a UI mistake. The second boot showed `Deserialization OK`, `TimeZone: Pacific/Auckland`, `NTP Server: nz.pool.ntp.org`, `Second blinking: 1`, and `REASON_SOFT_RESTART`. The ROM line `boot mode:(3,6)` is a normal flash boot. No boot loop or watchdog reset appeared.

## 9. Wi-Fi preservation

The flash wrote only `0x000000–0x076FFF`. The ESP8266 SDK Wi-Fi credentials are stored near the end of flash (`0x3FD000–0x3FFFFF` in the 4M2M layout) and were not touched, which is why the device reconnected to the original network without reconfiguration.

This is not a general guarantee:

- full-chip erase, a full 4 MB image write, a layout/Flash-size change, `wm.resetSettings()`, or a different SDK parameter format can remove or invalidate credentials;
- the K4-03 factory backup contains those credentials and must be protected.

## 10. Result and remaining work

**Passed (software path):** build, flash, automatic + independent verification, first boot, web UI reachability, configuration save/reload, `Pacific/Auckland`/`nz.pool.ntp.org` config, Wi-Fi credential preservation, soft restart.

**Partial / not recorded:** detailed display segment mapping, second-LED behaviour, RTC retention after network loss, automatic-brightness polarity/response, long-term stability, watchdog under network loss. The maintainer reported that the device looked normal, but no detailed test results are in the supplied log.

Known risks to check on the K4-03:

- GPIO15 is the 74HC595 OE (active-low) and a boot strap pulled low; outputs may be enabled briefly before `displaySetup()` raises OE. Watch for random segments at reset.
- The display mapping is hard-coded (active-low, LSB-first, digit1→digit4); a K4-03 revision could differ.
- Automatic brightness uses `A0 / 4` as an inverted PWM value; the light-sensor polarity may differ.
- DS3231 detection is not explicitly logged; verify offline time retention.
- The blue board LED is not controlled by the firmware.
- `Pacific/Auckland` is present in AceTime's TZDB 2023d and handled NZ DST at deployment time; future law changes need a timezone-database update.
- Security: AP password `password`, no web-UI authentication, predictable OTA password, plaintext UDP syslog default. Use only on a trusted LAN.

## 11. Reproduction

Use the [deployment runbook](../modules/deployment/README.md) with this record's unit-specific values. The non-negotiable points are:

1. Full 4 MiB backup of the exact unit, two reads matching, hash stored privately.
2. Flash only with `--before no-reset --after no-reset` and GPIO0 low; no automatic reset.
3. No full-chip erase for a sketch-only update.
4. Use the combined image at `0x000000`; verify both automatically and independently.
5. Power-cycle manually, remove GPIO0 from GND, and capture the 115200 application log.
6. Configure the timezone/NTP after first boot; the defaults are Europe/Budapest and `hu.pool.ntp.org`.
7. Keep the K4-03 backup and firmware image hashes together.
