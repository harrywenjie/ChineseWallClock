# 2026-07-23 K4-03 部署记录

本页根据 maintainer 提供的 Codex chat log 重建实际 fork 部署。它记录替换固件在 **BAIYANGSHU WiFi Clock K4-03**（不是 upstream K2-02）上的成功刷写。

## 1. 来源与隐私

- **来源：** maintainer 于 2026-11-08 提供的 Codex session log。部署日期由 maintainer 确认为 **2026-07-23**；chat 里 shell 时间戳为 14:52，build artifact 与同一天一致。
- **脱敏：** 公开记录去掉 MAC、Wi-Fi SSID、LAN 地址、AP chip suffix 和私有 backup path。这些值保留在 maintainer 的私有笔记里；不要加回仓库。
- **Backup 警告：** 完整 K4-03 factory backup 含已保存的 SDK Wi-Fi 配置，不只是固件。不能复制进 Git、作为 issue 附件或公开分享。

## 2. 目标硬件

| 项目 | 值 |
|---|---|
| Clock board | BAIYANGSHU WiFi Clock **K4-03**（实际机器） |
| Upstream 参考 | BAIYANGSHU 1902 WiFi Clock **K2-02**（不要假设电气等价） |
| MCU | ESP8266EX，26 MHz crystal |
| Flash | 4 MB |
| USB-UART | `COM3` 上的 Silicon Labs CP210x |
| 时钟供电 | 自己的 USB-A；CP2102 `+5V`/`3V3` 不接 |
| UART 接线 | CP2102 `GND` → board `GND`；CP2102 `TXD` → board `RXD0`；CP2102 `RXD` → board `TXD0` |
| Flash mode | manual：`FLASH`/GPIO0 → `GND`，再重新上电 |
| Reset 线 | CP2102 `RST`/`DTR`/`RTS` 不接；**没有自动 reset** |

部署时确认 6-pin header：pin 1 `FLASH`/GPIO0、pin 2 可能 `RST`、pin 3 `GND`、pin 4/5 `RXD0`/`TXD0`、pin 6 `+5V`。刷写前 UART 已测试。

因为没有自动 reset，所有 esptool 命令都带：

```text
--before no-reset --after no-reset
```

## 4. Build

- Build system：Arduino sketch，Arduino CLI。
- 最终工具：Arduino CLI **0.35.3**（Arduino IDE 2.3.2 内置版本）。
- Core：ESP8266 **3.1.2**。
- Libraries：仓库 `libraries/libraries.zip` 快照；没有换 latest。
- FQBN：`esp8266:esp8266:d1_mini`。
- Board 参数：80 MHz CPU、4 MB flash、`4M2M` layout（2 MB LittleFS、约 1019 KB OTA sketch）、DIO、40 MHz、lwIP v2 Lower Memory、32 KB cache + 32 KB IRAM、exceptions/debug/stack protection off、`-Os`、NONOS SDK 2.2.x_190703、xtensa-lx106 GCC 10.3。
- 可复现性：ESP8266 core 嵌入 build timestamp。最终 build 固定 `SOURCE_DATE_EPOCH=1711661163`（最后固件源码 commit 时间，2024-03-28T22:26:03+01:00）。两次 independent clean build 产出 byte-identical `.bin`。
- 最终 image：`temp/artifacts/canonical1/ChineseWallClock.ino.bin`（构建时路径），**485,280 bytes**，SHA-256 `5E4F281421DCE894FED3F03DD9599AF8A690218A85C70B6A5A5DB466748D3D1D`；可按 [toolchain setup](../modules/build-and-flash/toolchain-setup.md) 重建并复核。
- 其他产物：ELF 7,910,136 bytes；map 4,689,021 bytes；verbose log 保留在 [`build-canonical-ide232-cli.log`](2026-07-23-fork-build/build-canonical-ide232-cli.log)。
- 资源：RAM 37,404 / 80,192（46 %），IRAM 62,551 / 65,536（95 %），flash code 443,980 / 1,048,576（42 %）。
- Upstream v1.1 是 485,248 bytes；32-byte 差异未解决。Image header 同类（ESP8266、4 MB、DIO、40 MHz）。

Image 是单一 combined image：eboot 在 `0x000000`，application 在 `0x001000`；app ELF entry `0x401000C0`，IROM `0x40201010`（443,980 bytes）。没有独立 filesystem image；Web UI 编译在 WiFiManager 里。

## 5. 刷前检查

写之前重新校验 backup 和 firmware hash，确认 bootloader 连接，关闭 serial monitor。Flash 命令准备条件：

- 不做 full-chip erase；
- 不单独上传 filesystem；
- `--before no-reset --after no-reset`；
- 保守 `115200` baud；
- `--flash-mode keep --flash-freq keep --flash-size keep`，保留现有 flash 参数。

## 6. Flash 命令与结果

```powershell
py -m esptool --chip esp8266 --port COM3 --baud 115200 `
  --before no-reset --after no-reset `
  write-flash `
  --flash-mode keep --flash-freq keep --flash-size keep `
  0x000000 `
  E:\ChineseWallClock\temp\artifacts\canonical1\ChineseWallClock.ino.bin
```

结果：

- 只擦除 image 需要的扇区：`0x000000–0x076FFF`。
- 写入 **485,280 bytes**。
- esptool 自动校验：`Hash of data verified`。
- 独立校验：

```powershell
py -m esptool --chip esp8266 --port COM3 --baud 115200 `
  --before no-reset --after no-reset `
  verify-flash 0x000000 `
  E:\ChineseWallClock\temp\artifacts\canonical1\ChineseWallClock.ino.bin
```

返回 `Verification successful (digest matched)`。

这里的 image 路径是部署时 workspace 路径；重建后先复核 §4 的 size/SHA-256，再刷写。

- 没有 full-chip erase。
- 校验后设备仍在 bootloader。

```json
{"device_name":"HalClock","ntp_server":"nz.pool.ntp.org","timezone":"Pacific/Auckland","syslog_server":"","second_blinking":"true","leading_zeros":"true","auto_brightness":"true","brightness":"255"}
```

`clever` 缺失是已知 `saveConfiguration()` 缺陷，不是 UI 错误。第二次 boot 显示 `Deserialization OK`、`TimeZone: Pacific/Auckland`、`NTP Server: nz.pool.ntp.org`、`Second blinking: 1`、`REASON_SOFT_RESTART`。ROM 行 `boot mode:(3,6)` 是正常 flash boot。没有 boot loop 或 watchdog reset。

## 9. Wi-Fi 保留

Flash 只写 `0x000000–0x076FFF`。ESP8266 SDK Wi-Fi 配置在 flash 末尾附近（4M2M layout 的 `0x3FD000–0x3FFFFF`），没有被触碰，所以设备不用重配就连回原网络。

这不是普遍保证：

- full-chip erase、完整 4 MB image 写入、layout/Flash-size 改变、`wm.resetSettings()` 或不同 SDK 参数格式都可能删除/失效配置；
- K4-03 factory backup 含该配置，必须保护。

## 10. 结果与剩余工作

**Passed（software path）：** build、flash、自动 + 独立 verify、首次 boot、Web UI 可达、配置 save/reload、`Pacific/Auckland`/`nz.pool.ntp.org`、Wi-Fi 保留、soft restart。Maintainer 还确认 Wi-Fi 复用、configuration AP 关闭、断网后自动恢复；RTC/Wi-Fi 路径未分别 instrument。

**Partial / 未记录：** 详细 display segment mapping、秒点 LED、长期稳定性、断网 watchdog、auto-brightness 根因。Maintainer 发现自动亮度**偏暗**，改用固定 manual brightness；fixed 值和 A0 测量未记录。初次目视正常，但没有详细 display test。

K4-03 需要检查的风险：

- GPIO15 是 74HC595 OE（active-low）和低 boot strap；输出可能在 `displaySetup()` 拉高 OE 前短暂使能。reset 时注意随机段。
- Display mapping 硬编码（active-low、LSB-first、digit1→digit4）；K4-03 revision 可能不同。
- 自动亮度用 `A0 / 4` 作为 inverted PWM；本机偏暗。没有 A0/PWM 测量前不能证明原因。
- DS3231 detection 没有明确 log；maintainer 说断网能自动恢复，但 RTC-only 路径应单独测。
- 蓝灯不受固件控制。
- `Pacific/Auckland` 在 AceTime TZDB 2023d 中存在，部署时能处理 NZ DST；未来法律变化需要更新 timezone database。
- 安全：AP password `password`，Web UI 无认证，OTA password 可预测，默认 plaintext UDP syslog。只在可信 LAN 使用。

## 11. 复现

用 [deployment runbook](../modules/deployment/README.md) 和本记录的 unit-specific 值。不可妥协的点：

1. 对 exact unit 做完整 4 MiB backup，两次读取一致，hash 私有保存。
2. Flash 必须 `--before no-reset --after no-reset` 且 GPIO0 low；没有自动 reset。
3. sketch-only update 不做 full-chip erase。
4. 用 `0x000000` 的 combined image；自动和独立 verify 都做。
5. 手动 power-cycle，移除 GPIO0 到 GND，捕获 115200 应用 log。
6. 首次 boot 后配置 timezone/NTP；default 是 Europe/Budapest 和 `hu.pool.ntp.org`。
7. Backup 和 firmware image hash 放在一起。见 [backup manifest](2026-07-23-k4-03-backup-manifest.md)。
8. 在实际机器上检查 auto brightness；K4-03 偏暗，固定亮度是有效 fallback。
